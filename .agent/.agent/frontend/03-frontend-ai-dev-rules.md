# 规则 3：AI 前端开发行为约束

> 适用范围：AI 在前端项目中的一切代码生成与修改行为（页面 / 组件 / 样式 / 状态 / 请求 / 构建）。
> 目标：明确"什么可以交给 AI、什么必须人工"，防止 AI 私自改动前端高危逻辑，保证代码质量与项目风格一致。
> 前置：先加载 `microservice/01-core-agent-rules.md`；通用行为底线见 `management/01-ai-behavior-rules.md`，本文不重复。

---

## 1. 职责边界：AI 可以做什么、不可以做什么

### 1.1 AI 允许做（授权范围）
- 按已确认的 UI 稿、接口契约、组件规范，**实现**页面、组件、样式与交互。
- 编写单元测试、组件测试。
- 修复已定位的、非高危模块的缺陷。
- 生成 api 层调用封装、类型定义、表单校验、列表分页等**机械性、模板化**代码。
- 依据现有组件库、工具函数、hooks 复用代码，而非重复造轮子。
- 在 lint / type-check / test 通过后交付。

### 1.2 AI 禁止触碰（必须人工，或人工确认后 AI 才可辅助）
以下**前端高危逻辑**，AI 不得擅自生成、修改、删除，必须先经人工确认：

| 高危域 | 具体范围 |
|--------|----------|
| 路由与权限 | 路由表、动态路由、路由守卫、菜单 / 按钮权限控制 |
| 全局状态 | Pinia store 的 state 结构、持久化策略、跨页共享数据流 |
| 资金 / 支付 | 金额分↔元转换与展示、支付唤起、支付结果回调、订单流程页面 |
| 埋点上报 | 埋点事件定义、上报参数、隐私合规声明 |
| 敏感信息 | 手机号 / 身份证 / 银行卡的脱敏展示与存储；禁止明文日志与响应 |
| 接口契约 | api 层请求封装、响应拦截器、全局错误码映射、类型定义 |
| 依赖 | `package.json` / 锁文件新增或升级依赖 |
| 构建配置 | `vite.config.ts`、`tsconfig.json`、环境变量、代理、CDN 路径 |

### 1.3 需人工评审的特殊情况
出现以下情形时，AI 必须**停下并请求人工评审**，不得自行决定：
- 需要修改全局状态结构、路由结构、权限模型。
- 需要改动 api 层公共封装（拦截器、错误处理、鉴权头）。
- 需要引入新的第三方库、新的设计模式或状态方案。
- 一次改动超过 3 个文件且逻辑不相关。
- 对既有测试的修改（尤其删改断言使测试"变绿"）。

## 2. 代码风格与命名约束

- AI 生成的代码风格必须与**项目现有代码完全一致**，禁止自创风格、自创命名、自创目录。
- 遵循现有约定：文件 kebab-case、组件 PascalCase、变量/函数 camelCase、CSS 类名 BEM（详见规则 4）。
- 注释遵循项目风格（中文业务注释 + 导出符号注释），禁止照搬英文模板或缺失注释。
- 金额一律「分」整数（`number`），展示用统一工具 `formatFen` 转元，禁止页面内手写转换、禁止 float 参与金额计算。

---

## 3. 代码质量约束

1. **复用优先**：优先复用现有组件库（Vant / Element Plus）、`src/api` 封装、`composables/` hooks、`utils/` 工具函数，禁止重复实现相同能力。
2. **显式处理异常与边界**：loading、error、空态、超时、请求竞态（防旧响应覆盖）必须显式处理，禁止只写 happy path。
3. **禁止硬编码**：魔法数字、文案、URL、密钥一律走常量 / 配置 / 环境变量，禁止写死。
4. **禁止废弃 / 死代码**：不生成未使用组件、未使用导入、死代码、注释掉的废弃逻辑。
5. **组件与嵌套**：单文件职责单一、模板不宜过长；复杂逻辑拆分为组件 / composables。
6. **临时调试代码**：临时 `console.log` / 调试样式必须显式标注，提交前清理干净。
7. **禁止 any 糊弄**：新代码禁止用 `any` 绕过类型检查；确需时加豁免注释并交人工评审。

---

## 4. 禁止行为（完整清单）

- ❌ 未经确认直接改动 `package.json` / 锁文件 / `vite.config.ts`。
- ❌ 直接改写 api 拦截器、全局错误处理、鉴权头注入。
- ❌ 在页面组件里塞大量业务逻辑，不分层（直接改 store、直接发请求、手写金额转换）。
- ❌ 用 `console.log` 代替调试工具，提交未清理。
- ❌ 只写 happy path，不处理 loading / error / 空态 / 竞态。
- ❌ 修改测试断言让用例"通过"，而非修复被测代码。
- ❌ 删除或注释既有测试，以绕过失败。
- ❌ 引入与现有实现重复的工具函数 / 组件 / hooks。
- ❌ 写死接口地址、密钥、埋点参数；把密钥放进前端环境变量。
- ❌ 复制粘贴其他项目 / 网上代码不经审查直接落地。
- ❌ 修改路由守卫 / 权限逻辑不经人工确认。
- ❌ 提交未清理的调试日志、`console.log`、临时文件。
- ❌ 在 `pnpm build` 未通过的情况下声称"完成"。

---

## 5. AI 交付自查清单

AI 每次交付代码前必须自查并说明：

- [ ] 改动范围是否与任务一致，未夹带无关改动
- [ ] 是否触碰了高危域（若是，是否已人工确认）
- [ ] 是否复用了现有组件 / api 封装 / hooks / 工具函数
- [ ] loading / error / 空态 / 竞态是否显式处理
- [ ] 是否硬编码了任何魔法数字 / 文案 / 接口地址 / 密钥
- [ ] `lint` / `type-check` / `test` / `build` 是否全部通过
- [ ] 临时调试代码是否已清理
- [ ] 是否有 `any` / 未使用导入 / 死代码
