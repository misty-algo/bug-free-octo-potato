## 这份文档怎么读

每一步都按同一个模板展开：

```

       ├─ 注意      ⚠️ 易错点
       └─ 验证      怎么证明它对
```

**一次开发的粒度**：一张任务书（1–3 天），只做该步列出的接口。

### 三条铁律

1. **主线永远可跑通**。任何时候 `main` 上：能登录 → 能估价 → 能下单 → 能派单 → 能走完 → 能付款。断一天，六个人就开始互相等。
2. **依赖没就位不许提前做**。表里"本次不做"的东西，一个都不要顺手写 —— 提前做等于做两遍。
3. **碰钱、碰状态、碰并发的改动必须带测试**。

### 接口地址约定

| 项 | 约定 |
|---|---|
| 前缀 | `/api/v1`（网关注册统一加版本；接口文档原文写 `/api/xxx`，实现时补成 `/api/v1/xxx`） |
| 本地 | `http://127.0.0.1:8080` |
| 测试/生产 | 读环境变量 `API_BASE_URL`，禁止硬编码 |
| 免鉴权接口 | 仅 `3.1.1`、`3.1.2`、`3.5.3`（3.5.3 虽免鉴权但**必须验签**） |
| 路径参数 | `{}` 为必填，如 `/api/v1/pax/orders/{order_id}` |
| 前缀含义 | `auth`=公共认证 · `pax`=乘客 · `drv`=司机 · `admin`=管理端 · `callback`=三方回调 · `events`=事件查询 |

## 第 2 步 · 让人能登录并且不掉线（2d，D1）

### 这一步在解决什么问题

后面 68 个接口全部要求 `Authorization: Bearer {token}`。**没有令牌，其他所有人一个接口都调不通**，六个人只能干等。所以这一步必须先做。

`refresh` 为什么紧跟 `login`：访问令牌只有 30 分钟。如果先做完一堆接口再补刷新，中间每次联调跑半小时就集体 401 —— 而且这种报错极容易被误判成业务 bug，排查成本极高。

---

### 接口 2-1：发送短信验证码（文档 3.1.1）

- **接口地址**：`POST /api/v1/auth/sms/send`
- **作用**：登录/换绑的入口。下发验证码，返回重发倒计时。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| phone | string | 是 | 手机号 |
| scene | string | 是 | `login` / `change_bind` |

- **出参**：`{ retry_after: 60 }`（60 秒倒计时）
- **落库**：`account`、`channel_binding`；**限流计数走 Redis TTL，不落库**
- **规则**：
  1. 验证码 5 分钟有效
  2. 60 秒内不可重发
  3. 同一手机号 + 同一设备，每小时最多 5 次
  4. 连续输错 5 次 → 锁定 30 分钟
  5. 验证码使用后立即失效，不可复用
  6. **验证码只在服务端比对，响应里绝不能带上正确答案**
- **注意** ⚠️
  - 限流/锁定窗口用 Redis TTL 实现；**不要**用数据库行锁 —— 高频接口会打爆连接池
  - 日志里手机号打 Mask（`138****6688`），不打明文
- **验证**：同号码 60s 内重发返回倒计时；同设备第 6 次被拒；连错 5 次后第 6 次报锁定

---

### 接口 2-2：登录（三渠道）（文档 3.1.2）

- **接口地址**：`POST /api/v1/auth/login`
- **作用**：把"渠道身份"换成"本平台账号 + 会话令牌"，并告诉客户端登录后该去哪一页。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| channel | string | 是 | `wechat` / `qq` / `sms` |
| auth_code | string | 微信/QQ 时必填 | 授权码 |
| phone | string | sms 时必填 | 手机号 |
| sms_code | string | sms 时必填 | 验证码 |
| role | string | 是 | 会话角色 `pax` / `drv` |

- **出参**：`{ access_token, refresh_token, role, restore_target: { type, order_id } }`
- **落库**：`account`、`channel_binding`、`session_token`、`order`（算恢复目标）、`bill`（算恢复目标）
- **规则**：
  1. **微信/QQ 必须用授权码在服务端换渠道唯一标识**，禁止前端传用户 ID
  2. 一个主账号可同时是乘客和司机，登录时只能选一个会话角色
  3. 手机号已存在时，**必须先验证原账号再绑渠道**，禁止按昵称自动合并账号
  4. 令牌 payload 携带角色，且服务端每次请求都校验
  5. 三端受众隔离（`pax` / `drv` / `admin`），**角色切换必须重新登录**
  6. `restore_target` 由服务端计算：活动行程 > 未付账单 > 默认页
- **注意** ⚠️
  - 这是**最容易出事故的接口**：如果按昵称/手机号直接合并账号，会出现 A 用户看到 B 用户行程的越权
  - `restore_target` 在这一步**只返回 `default`**，前两个分支要等账单域做完（第 15 步）再回填，别在这里写死
- **验证**：三个渠道各登录成功；同手机号换绑后登录指向同一 account

---

### 接口 2-3：刷新会话令牌（文档 3.1.4）

- **接口地址**：`POST /api/v1/auth/refresh`
- **作用**：access 过期后用 refresh 换新，不打断用户操作。
- **入参**：`{ refresh_token }`
- **出参**：`{ access_token, refresh_token }`
- **落库**：`session_token`
- **规则**：
  1. access 30 分钟、refresh 7 天
  2. **刷新时轮换令牌**：旧的 refresh 立即失效
  3. 受限 / 注销账号收敛可用动作
- **注意** ⚠️
  - 轮换不落地 = refresh 可无限重放 = 令牌泄漏后无法止损
- **验证**：access 过期后 refresh 成功；旧 refresh 再用报无效

### 接口 2-3 附：退出登录（文档 3.1.5）

- **接口地址**：`POST /api/v1/auth/logout`
- **作用**：撤销刷新令牌。
- **入参**：`{ refresh_token }`
- **出参**：`{ revoked: true }`
- **落库**：`session_token`
- **规则**：退出撤销 refresh，access 自然过期（不做令牌黑名单）。
- **注意** ⚠️：只撤 refresh 是约定，不是偷懒；若要即时生效需额外维护黑名单，本期不引入。

### 接口 3-1：绑定/解绑渠道（文档 3.1.6）

- **接口地址**：`POST /api/v1/auth/binding`
- **作用**：把第三方渠道（微信/QQ/手机号）挂到主账号上，或摘掉。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| action | string | 是 | `bind` / `unbind` |
| channel | string | 是 | `wechat` / `qq` / `sms` |
| old_sms_code | string | 换绑时 | 旧手机验证码 |
| new_sms_code | string | 换绑时 | 新手机验证码 |

- **出参**：`{ bindings: [ { channel, bound } ] }`
- **落库**：`channel_binding`
- **规则**：
  1. 换绑必须**新旧两端短信都校验通过**
  2. 解绑后必须至少保留一种登录方式
  3. `渠道 + 渠道用户标识` 唯一约束
- **注意** ⚠️：解绑校验是"解绑后剩余方式 ≥1"，不是"当前有多少种"，两者在换绑中间态下不同。
- **验证**：换绑新旧双码齐全才通过；只剩一种登录方式时解绑被拒。

### 接口 3-2：实名认证（文档 3.7.1）

- **接口地址**：`POST /api/v1/pax/realname`
- **作用**：把账号变成"可下单账号"。**下单的前置条件**。
- **入参**：`{ name, id_no, idempotency_key }`
- **出参**：`{ state: 认证中 / 已认证 / 认证失败 }`
- **落库**：`real_name_auth`
- **规则**：
  1. 每账号每天最多 3 次**有效提交**
  2. 同一证件只能绑定一个有效主账号
  3. 通过后脱敏展示且**不可修改**
  4. 状态机：未认证 → 认证中 → 已认证 / 认证失败
  5. 超时保留"认证中"并主动查询结果
  6. **重复请求不消耗次数**（靠 `idempotency_key`）
- **注意** ⚠️
  - 证件号必须走敏感三件套：`idNoEnc`（AES-256-GCM）+ `idNoHash`（等值查询/唯一索引）+ `idNoMask`（展示）
  - 日志里禁止出现完整证件号
- **验证**：同证件绑第二个账号被拒；重复提交 10 次只消耗 1 次配额。

- **接口地址**：`POST /api/v1/pax/account-security`
- **作用**：乘客角色下的绑定列表 + 协议版本记录，复用 3.1.6 的能力。

## 第 4 步 · 让系统能算对一个价格（3d，D5）

### 这一步在解决什么问题

估价、账单、取消费、退款四处都要调计价引擎。**引擎写错，四处全错**，而且错的金额会一路带进资金流水，对账时才发现，已经来不及。所以引擎必须最先写、最先测。

计价发布接口（3.13.1）虽然是管理端接口，但它是**引擎唯一的输入来源**，必须紧跟其后 —— 没有已发布的配置，第 14 步估价无价可算。

### 计价引擎公式（唯一公式）

```
T = start + Round((dist - incl) * perKm, 1000) + Round(dur * perMin, 60)
Q = Round(T * surgeBp, 10000)            （拼车再乘 discountBp）
H = Round(Q * serviceBp, 10000)           （乘客服务费）
K = Round(Q * commBp, 10000)              （司机佣金）
F = Q + H                                 （原车费）
P = F - Cp - Cd                           （乘客应付）
D = Q - K - Cd                            （司机应得）
N = H + K - Cp                            （平台净额）
资金守恒：P = D + N + G
退款尾差：Round(D0 × (Rp + r), P0) − Round(D0 × Rp, P0)
```

### 接口 4-1：计价规则管理（文档 3.13.1）

- **接口地址**：`POST /api/v1/admin/pricing/publish`
- **作用**：发布一版生效的计价配置，并给出样例分账预览。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| config | object | 是 | 按城市区域 + 车型配置起步价、里程价、时长价、服务费、佣金、溢价、固定价、取消费 |
| valid_from / valid_to | int | 是 | 生效区间 |
| priority | int | 否 | 区域优先级 |

- **出参**：`{ cfg_version: 2 }`
- **落库**：`pricing_config`
- **规则**：
  1. **乘客服务费与司机佣金是两个独立字段**，不是一个费率拆两半
  2. 草稿校验通过后才发布新版本，并指定生效区间
  3. **生效版本不可原地修改**，历史订单用快照
  4. 发布前展示**至少三个样例**的分账结果
  5. 区域重叠按 `priority` 选一；**同优先级时间重叠禁止发布**
  6. 无有效价 → 停止该车型新单估价并告警，不许"估算个大概"
  7. 样例预览必须与文档第四章五个校验例**精确一致**（T08）
- **注意** ⚠️
  - `Round` 的除数固定：距离 1000、时长 60、费率 10000
  - `bp` 是万分比整数（`service_bp=600` = 6%），不是百分比
  - 全链路金额 `int64`，**代码里出现 `float` 一律打回**
- **验证**：5 个校验例表驱动测试逐个断言到分；权重和 ≠10000 拒绝保存

## 第 5 步 · 让乘客能选到起点和终点（1.5d，D3）

### 这一步在解决什么问题

估价需要 `start_id` / `end_id` 两个 POI。所以 POI 必须排在估价之前。地址簿排在这里，是因为它是首页的一个数据源，顺手一起做完，避免第 6 步做首页时再来回改。

### 接口 5-1：POI 搜索（文档 3.2.2）

- **接口地址**：`GET /api/v1/pax/poi/search`
- **作用**：让乘客把"我想去的地方"变成系统里的一个点。
- **入参**：`keyword`(必填)、`lng` / `lat`(选填，定位，用于按距离排序)
- **出参**：`{ pois: [ { id, name, addr, city, lng, lat, distance } ] }`
- **落库**：`poi`
- **规则**：
  1. 关键词返回**前 10 条**
  2. 带定位时按距离排序
  3. **无坐标时仍返回，但不显示虚假距离**
- **注意** ⚠️
  - 坐标 GCJ-02，落库 GeoJSON `{ type:"Point", coordinates:[lng,lat] }`，建 2dsphere 索引，禁止自造 lat/lng 双字段
  - "没有坐标就不给距离"是硬要求 —— 编一个距离出来比不显示更糟
- **验证**：关键词命中名称与地址；按城市过滤；无坐标时 `distance` 为空

### 接口 5-2：常用/历史地址管理（文档 3.2.3）

- **接口地址**：`GET`（查询）/ `POST`（增改删清空）`/api/v1/pax/address`
- **作用**：保存家和公司，以及从历史订单里沉淀的上车点。
- **入参**：`action`(`save`/`delete`/`clear`)、`type`(家/公司/其他)、`name` / `addr` / `poi_id`
- **出参**：`{ common: [], history: [] }`
- **落库**：`address_book`
- **规则**：
  1. 常用地址**最多 20 条**
  2. 历史地址按选择次数 + 最近使用时间排序，展示**前 10 条**，可清空
  3. **按账号隔离做对象级授权**

## 第 6 步 · 首页聚合与车型（1d，D3）

## 第 7 步 · 让订单能落下来（3d，D3）★主线关键

### 这一步在解决什么问题

把"估价"变成"订单"，并且**发出 `OrderCreated` 事件**。这一步是所有后续（派单、行程、账单）的起点。

**为什么券在这里先不做**：券锁定必须和订单创建在同一事务里。如果现在做，第 24 步券模板/发放还没设计好，锁定接口会返工。先跑通无券主链路，第 24 步一次性回填，只改 3 处。

---

### 接口 7-1：预估计价（文档 3.3.2）

- **接口地址**：`POST /api/v1/pax/estimate`
- **作用**：下单前给出预估价、里程时长、费用构成，并生成一个有 5 分钟寿命的估价单。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| start_id | int | 是 | 上车点 POI |
| end_id | int | 是 | 目的地 POI |
| type | string | 是 | 车型 |
| seats | int | 否 | 拼车人数 |

- **出参**：`{ estimate_id, dist_m, dur_s, price: {T,Q,H,F,K,fixed}, payable, coupon_id, expires_at, cfg_version }`
- **落库**：`estimate`（+ 读 `pricing_config` / `poi` / `coupon`）
- **规则**：
  1. **估价有效 5 分钟**
  2. 快照必须含：价格版本、起终点、车型、人数、优惠方案
  3. **有效期由服务端时间判断**；数据库 TTL 只做存储清理，**不充当校验**
  4. 计程单注明"按实际计费"；**仅固定价承诺堵车不加价**
  5. 默认自动选最优可用券（本轮恒为空）
- **注意** ⚠️
  - 用 DB TTL 当过期校验是最常见的坑：TTL 清理有延迟，过期估价仍能被消费
  - `cfg_version` 必须落进快照，否则改价后历史订单金额会被回溯
- **验证**：5 分钟后用同一 `estimate_id` 下单 → 拒绝；两个车型返回两套价

---

### 接口 7-2：创建订单（文档 3.3.3）

- **接口地址**：`POST /api/v1/pax/order`
- **作用**：把估价单变成一张真订单，并触发派单。
- **入参**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| estimate_id | string | 是 | 估价单 id |
| idempotency_key | string | 是 | 幂等键 |
| coupon_id | string | 否 | 券 id（null = 不用券） |
| remark | string | 否 | 备注（≤50 字） |

- **出参**：`{ order_id, state, type, price_snap, matching }`
- **落库**：`estimate`（置 `used`）、`order`、`coupon`（本轮不动）、`order_timeline`、`event_log`(outbox)
- **规则**：
  1. **前置校验**：实名通过 + 无活动行程 + 无未结清账单，才可下单
  2. **幂等下单**：相同 `idempotency_key` 重试返回**同一订单**
  3. **估价单最多消费一次**，与券锁定、事件写入在**同一事务**完成
  4. 普通单首次派单窗口 **120 秒**
  5. 拼车单进入 **60 秒匹配封组**（同起终点 POI、同城市、同计价方案）
  6. 唯一约束兜底：一用户一个活动订单
- **注意** ⚠️
  - **`estimate` 置 `used` 必须是条件更新**（`WHERE used=0`），不能先查后写
  - 事件写 outbox 必须和建单同事务，否则会出现"有订单无派单任务"的悬空单
  - `state` 落库用 SSOT 枚举（`PENDING`），响应给前端可映射回 `WAITING`
- **验证**：同 key 连发 10 次 → `order` 只 1 行、`order_id` 相同；已有活动订单再下单被拒；outbox 有 `OrderCreated` 且 Kafka 有消费记录

---

### 接口 7-3：等待接单状态查询（文档 3.3.4）

- **接口地址**：`GET /api/v1/pax/order/wait-status`
- **作用**：推送断线时的轮询兜底，告诉乘客"还在等/已派到/还有多久"。
- **入参**：`order_id`(必填)
- **出参**：`{ state, deadline, driver_snap, matching_deadline }`
- **落库**：`order`、`dispatch_task`（只读）
- **规则**：
  1. 状态以**服务端推送**为主，此接口只是兜底
  2. 断线时每 **5 秒**拉取一次
  3. **恢复时先查当前状态，不以本地倒计时取消订单**
- **注意** ⚠️：客户端倒计时到了就自行取消 = 状态机被客户端驱动，绝对禁止
- **验证**：轮询无副作用；本轮返回 `PENDING`，派单接上后自然返回更多状态

## 第 8 步 · 让司机具备合法接单资格（2.5d，D2）

### 这一步在解决什么问题

派单的候选过滤里有一条"资质有效 + 车辆合规"。如果没有审核通过的司机，第 11 步的抢单并发测试根本没有数据可造 —— 你会以为代码写对了，其实只是没人可抢。

顺序刻意是：**提交申请 → 管理员审批 → 司机回读结果**。倒过来做，审批那一刻没有对象，测试只能造假数据。

---

### 接口 8-1：车辆资料提交（文档 3.11.1）

- **接口地址**：`POST /api/v1/drv/vehicle/application`
- **作用**：司机把车和人证信息报上来，生成一个等待审批的申请。
- **入参**：`plate` / `model` / `seats`、`cert_no` / `cert_expire`、`images`(6 张各 5MB)、`idempotency_key`
- **出参**：`{ application_id, revision, state }`
- **落库**：`vehicle_audit`、`vehicle`
- **规则**：
  1. 一名司机同时**只绑一辆有效车**，一辆车**只绑一个有效司机**
  2. 提交生成**不可变**审核版本；重新提交**追加 revision，不覆盖**历史驳回
  3. 终态裁决唯一（一个版本只能裁决一次）
  4. **驳回 3 次 → 标人工重点复核**
  5. 历史订单保留**旧车辆快照**
- **注意** ⚠️
  - 版本链是 append-only。任何"更新申请"的写法都会毁掉审计能力
  - 图片走 `pkg/filex` 统一上传，不要各域自己实现
- **验证**：同一 `application_id` 再提交 → revision+1，旧版本内容不可变

---

### 接口 8-2：司机与车辆审核（文档 3.12.2）

- **接口地址**：`POST /api/v1/admin/driver-audit`
- **作用**：管理员对一个申请版本做出通过/驳回裁决。
- **入参**：`application_id`、`revision`、`action`(`approve`/`reject`)、`reason`(驳回必填)、`version`(版本锁)
- **出参**：`{ application_id, state }`
- **落库**：`vehicle_audit`、`driver`、`event_log`
- **规则**：
  1. 领取申请**版本**审批（带 `revision`）
  2. 驳回**必须填原因**
  3. **提交人不能审批自己的资料**
  4. 并发审核用**版本锁**
  5. **准入联动**：通过后触发资质变化事件，由准入服务**全量重算**（全部证件有效 + 账号允许 + 车辆合规 才恢复接单），**不直接改司机状态**
- **注意** ⚠️
  - "通过后直接 `UPDATE driver SET status='active'`" 是最典型的越权写法：绕过了准入规则，司机会在资料不全的情况下被派单
  - 这一轮 admin 接口先用**固定超管账号**跑通，真 RBAC 放到第 26 步补
- **验证**：自审被拒；通过后司机端状态查询能看到新版本

---

### 接口 8-3：车辆审核状态查询（文档 3.11.2）

- **接口地址**：`GET /api/v1/drv/vehicle/status`
- **作用**：司机看自己审批到哪一步了，证件什么时候到期。
- **出参**：`{ current_version, cert_expire, remind_days }`
- **落库**：`vehicle_audit`、`vehicle`
- **规则**：
  1. 证件到期前 **30 / 7 / 1 天**提醒
  2. **有效旧证可用至到期**，新证审核中不能替代已到期旧证
  3. **途中到期不中断当前行程**
- **注意** ⚠️：到期判定用业务时间（`pkg/biztime`），不用机器时间，否则测不了"途中到期"
- **验证**：构造 29/6/1 天到期的证件，提醒各出现一次

## 第 9 步 · 让司机能在线接单（2d，D2）

### 这一步在解决什么问题

派单器只给"在线 + 心跳新鲜 + 无活动任务"的司机派单。这三个状态由本步的三个接口写入。

顺序：`status`（先出车）→ `heartbeat`（证明还活着）→ `region-preference`（限定片区）。区域偏好放在心跳之后，是因为它属于"过滤条件"而非"存活条件"。

---

### 接口 9-1：出收车/模式切换（文档 3.8.1）

- **接口地址**：`POST /api/v1/drv/status`
- **作用**：司机上线接单 / 下线收车，并切换听单模式还是抢单模式。
- **入参**：`action`(`online`/`offline`)、`mode`(`listen`/`grab`，选填)
- **出参**：`{ status, mode }`
- **落库**：`driver`
- **规则**：
  1. **上线前置**：资质有效 + 在开通城市 + 定位新鲜 + 无活动任务，四条缺一不可
  2. 司机四态：`offline` / `idle` / `busy` / `reserved`
  3. 模式切换 → **清空旧队列 + 递增模式版本，旧邀请即时失效**
- **注意** ⚠️
  - 模式版本不递增，会出现"听单时代的邀请"在抢单时代被接受，产生幽灵派单
  - 状态与任务占用必须**同事务更新**
- **验证**：未审核司机上线被拒；切换模式后旧 invite 立即失效

---

### 接口 9-2：心跳上报（文档 3.8.2）

- **接口地址**：`POST /api/v1/drv/heartbeat`
- **作用**：司机持续证明自己在线，并上报当前位置。
- **入参**：`lng` / `lat`（必填）
- **出参**：`{ alive: true }`
- **落库**：`driver`（+ Redis 活跃）
- **规则**：
  1. 状态与任务占用**同事务更新**
  2. **60 秒无心跳 → 收车**
  3. **忙碌掉线保留任务**（不能因为掉线把行程弄丢）
  4. 空闲连续 60 秒无心跳 → 收车
  5. 在线司机看板取**近 60 秒**心跳
- **注意** ⚠️：忙碌和掉线的处理是**相反**的 —— 忙碌保任务，空闲才收车。写反了会导致行程中司机被强制下线
- **验证**：停心跳 61 秒后状态变 offline；busy 状态下掉线任务保留

---

### 接口 9-3：区域偏好设置（文档 3.8.6）

- **接口地址**：`POST /api/v1/drv/region-preference`
- **作用**：司机限定只接某些片区的起点订单。
- **入参**：`enabled`(必填)、`regions`(必填，片区多选)
- **出参**：`{ enabled, regions }`
- **落库**：`driver`
- **规则**：
  1. **后台总开关**控制个人区域偏好是否生效
  2. 个人开关开启时，**仅匹配指定片区内起点订单**
  3. **边界点算区域内**
  4. 定位失效 30 秒 → **停止新派单**
- **注意** ⚠️：这里有两级开关（平台总开关 × 个人开关），必须两个都为真才生效
- **验证**：开启后只收到片区内任务；关闭总开关后个人设置失效

> 🚧 **门禁**：手工造 3 个「已审核 + 在线 + 有心跳 + 有区域」的司机。

## 第 10 步 · 派单配置与接单大厅（1.5d，D4）

### 这一步在解决什么问题

大厅要读 `dispatch_task`，而任务的阶段时长和排序权重来自配置。所以**配置在前、大厅在后**。配置写死在常量里是最省事的诱惑，但要忍住 —— 第 11 步的超时转派、第 27 步的改派都要读它。

---

### 接口 10-1：派单策略配置（文档 3.13.2）

- **接口地址**：`POST /api/v1/admin/dispatch/config`
- **作用**：定义派单的"时间预算"和"排队规则"。
- **入参**：`weights`(总和 10000)、`radius`(候选半径 5 公里)、`invite_sec`(15) / `total_sec`(120)、`region_switch`、`re_dispatch_params`
- **出参**：`{ config_version }`
- **落库**：`config_dictionary`（或独立 `dispatch_config` 表）
- **规则**：
  1. **先听单 60 秒，后转抢单 60 秒，总窗口 120 秒**
  2. **重派边界**：退单后继承剩余派单预算；每任务最多 1 次额外 60 秒窗口；每任务最多 2 次已接单退回，之后平台取消
  3. **单通道控制**：每任务任一时刻只有一个分发通道
  4. **阶段期限分别存储**，旧阶段定时器**不得取消新阶段**
  5. **权重校验**：全 0 或总和不等于 10000 → 拒绝保存
- **注意** ⚠️：第 4 条是派单最容易出隐蔽 bug 的地方 —— 听单超时后马上被抢单接走，如果旧阶段的超时定时器还能跑，会把新阶段的 `ASSIGNED` 覆盖成"超时取消"
- **验证**：权重和 9999 拒绝保存；构造"听单超时瞬间被抢"的场景，订单不被取消

---

### 接口 10-2：获取接单大厅数据（文档 3.8.3）

- **接口地址**：`GET /api/v1/drv/hall`
- **作用**：司机一屏看到自己的状态、待响应的邀请、预占、改终点请求和抢单池。
- **出参**：`{ status, mode, invite, reserve, change_req, pool }`
  - `invite`: `{ task_id, expires_at }`
  - `pool`: `[ { task_id, start_name, end_name, income, type_name, count, deadline } ]`
- **落库**：`driver`、`dispatch_task`、`order`、`poi`（只读）
- **规则**：
  1. 抢单模式显示**起终点、预估收入、接驾距离、订单类型**
  2. **不含乘客真实手机号**
  3. 合并一次返回，减少轮询
  4. 听单派发器**单通道**分发
- **注意** ⚠️：大厅数据是派单任务的**读模型**，不要在里面做任何状态推进；状态推进一律走 3.8.4 / 3.8.5
- **验证**：任务过期后不出现在 pool

## 第 11 步 · 让一单只能被一个人抢到（2.5d，D4）★最高风险

### 这一步在解决什么问题

这是全项目**唯一一个必须靠数据库约束而不是靠"逻辑正确"来兜底**的地方。100 个并发请求抢同一单，逻辑再对，只要缺唯一约束，就会出现两个司机同时被派同一单 —— 结果是双倍接送费、一个乘客两个司机到门口。

先做 3.8.4（邀请，单向无竞争）把"状态推进"这条通路验通，再做 3.8.5（抢单，高并发竞争）。

---

### 接口 11-1：听单邀请响应（文档 3.8.4）

- **接口地址**：`POST /api/v1/drv/invite/respond`
- **作用**：司机在被邀请的 15 秒窗口内做出接受或拒绝。
- **入参**：`task_id`(必填)、`accept`(bool，必填)
- **出参**：`{ task_id, assigned }`
- **落库**：`dispatch_task`、`order`、`driver`
- **规则**：
  1. **邀请 15 秒轮转**
  2. **同轮不重复邀请同一司机**
  3. **听单排序**：先过滤（城市 / 车型 / 座位 / 区域 / 资质 / 位置 / 占用），再按**本月累计已结算收入升序**；同值按距离、好评率、在线时长、成功率评分（0–10000 整数归一，权重来自 A06 且总和 10000）
- **注意** ⚠️
  - "收入升序"是为了把单派给挣得少的人，实现收入均衡 —— 写反了会让头部司机吃掉所有单
  - 评分必须是**整数归一**，别用 float
- **验证**：拒绝后同轮不再邀该司机；15 秒超时进下一轮

---

### 接口 11-2：抢单（预占/确认/放弃）（文档 3.8.5）

- **接口地址**：`POST /api/v1/drv/grab`
- **作用**：司机在抢单池里抢任务，分两步走：先原子预占 15 秒，再确认。
- **入参**：`task_id`(必填)、`action`(`reserve`/`confirm`/`abandon`，必填)、`version`(confirm 时必填，乐观锁)
- **出参**：`{ task_id, state }`
- **落库**：`dispatch_task`、`driver`、`order`
- **规则**：
  1. 点击抢单 → **原子预占任务与司机 15 秒**
  2. **数据库唯一约束**同时保障「一个任务一个司机」「一个司机一个活动任务」
  3. 配合 15 秒预占记录 + **版本复验**
  4. **不可仅靠缓存锁**（Redis 锁失效/重启会导致超派）
  5. **100 并发请求自测唯一性**（T04）
- **注意** ⚠️
  - Redis 锁只能做"削峰"，唯一性必须由数据库唯一约束保证
  - 预占超时释放要有补偿任务，不能只靠客户端不上报
- **验证**：100 goroutine 抢同单 → `assigned=1`；预占 15 秒未确认 → 释放且可被抢；一司机不能同时占两单；**连续跑 20 轮全绿**

## 第 12 步 · 让行程能从接驾走到送达（3d，D3）

### 这一步在解决什么问题

把订单从 `ACCEPTED` 推到 `ENDED`。这一步的关键是**位置上报必须先做** —— 到达的 200 米校验、送达的里程计算，全都依赖它。

### 接口 12-1：司机位置上报（文档 3.9.5）

- **接口地址**：`POST /api/v1/drv/position`
- **作用**：司机端持续上报位置，形成轨迹，供里程计算和乘客端查看。
- **入参**：`lng` / `lat`(必填)、`task_id`(选填)
- **出参**：`{ accepted: true }`
- **落库**：`order`（轨迹，Mongo）、`driver`
- **规则**：
  1. **5 秒**上报一次
  2. **无网络时本地缓存轨迹并标「待同步」**，恢复后补传
  3. **异常跳点样本进入计费校验，不直接累计里程**
- **注意** ⚠️
  - 跳点（GPS 漂移）直接累加里程 = 多收乘客钱。必须先过滤再累计
  - 轨迹量大，走 Mongo + TTL，不要塞进 MySQL 主表
- **验证**：构造跳点，里程不异常增长；断网补传后轨迹连续

---

### 接口 12-2：到达上车点确认（文档 3.9.1）

- **接口地址**：`POST /api/v1/drv/trip/arrive`
- **作用**：司机声明"我到了"，开始等待乘客上车。
- **入参**：`task_id`(必填)、`idempotency_key`(必填)、`reason`(异常到达时必填)
- **出参**：`{ task_id, state: ACTIVE, abnormal: bool }`
- **落库**：`dispatch_task`、`order`、`order_timeline`
- **规则**：
  1. **距上车点 ≤ 200 米**且**定位 ≤ 30 秒**，才允许常规确认
  2. 异常到达 → 填原因 + 生成复核标记
  3. **距离由服务端计算**（取司机最近定位与上车点）
  4. 幂等键保证重复提交只产生一条到达事件
- **注意** ⚠️：距离绝不能由客户端上报后直接采信，否则司机可以"远程到达"
- **验证**：距上车点 201m 请求被拒；重复到达时间线只 1 条

---

### 接口 12-3：乘客上车核验（文档 3.9.2）

- **接口地址**：`POST /api/v1/drv/trip/verify`
- **作用**：防止司机接错人 —— 用手机号后四位确认上车的是本人。
- **入参**：`order_id`(必填)、`code`(尾号后四位)
- **出参**：`{ order_id, verified, remaining_attempts, lock_until }`
- **落库**：`order`、`passenger`
- **规则**：
  1. **逐一核验**乘客手机号后四位，才开始行程
  2. **连续 5 次错误 → 锁 10 分钟**
  3. **比对只在服务端完成，不向司机端返回正确答案**
  4. 锁定期间禁止重试，提示联系乘客 / 客服
- **注意** ⚠️
  - 返回"正确答案"或"第几位错了"= 直接泄露乘客信息
  - 拼车要**逐单**核验（每单 `boarded_at`）
- **验证**：连错 5 次后返回 `lock_until`；响应体内不含正确尾号

---

### 接口 12-4：开始行程（文档 3.9.3）

- **接口地址**：`POST /api/v1/drv/trip/start`
- **作用**：正式发车，开始计费，锁定价格快照。
- **入参**：`task_id`(必填)、`idempotency_key`(必填)
- **出参**：`{ task_id, state, departed_at }`
- **落库**：`dispatch_task`、`order`、`order_timeline`
- **规则**：
  1. **开始幂等**
  2. 记录：时间、位置、轨迹起点、**价格快照**
  3. 拼车：逐单核验上车，记录 `boarded_at`；司机确认「开始共同出发」记任务发车时间
- **注意** ⚠️：未核验（12-3）不许发车，这是硬性前置
- **验证**：未 verified 的订单调 start → 拒绝；重复 start 返回同一 `departed_at`

---

### 接口 12-5：确认送达/结束行程（文档 3.9.4）

- **接口地址**：`POST /api/v1/drv/trip/end`
- **作用**：停止计费，发出 `TripEnded` 事件（账单由第 13 步的消费者生成）。
- **入参**：`order_id`(必填)、`actual_dist`(必填，米)、`actual_dur`(必填，秒)、`idempotency_key`(必填)、`end_reason`(安全提前结束时必填)
- **出参**：`{ order_id, state: ENDED, bill }`
- **落库**：`order`、`event_log`(outbox)；**不写 `bill`**
- **规则**：
  1. 送达停止计费，生成最终账单（**由 billing 域消费事件生成**）
  2. 提前结束记录原因与实际终点
  3. **送达幂等**：重复请求返回原结果，不二次计费
  4. 拼车：**逐单送达、逐单计费**
  5. 完单按结束日计数；收入待支付后按记账日入账
- **注意** ⚠️
  - **订单域不许直接写 `bill`**。这是最容易破坏域边界的一步 —— 看似只是"顺手生成账单"，实际上把计价规则耦合进了订单服务
  - 事件已可靠落库，所以账单可以回放补生成，不会丢
- **验证**：重复送达返回同一结果；outbox 有 `TripEnded`

### 第 11–12 步 · 完成标志

- 能人工从"抢到单"走到"已送达"。
- 此时 `order.state=ENDED`，**还没有 bill** —— 这是对的，不是 bug。

## 第 13 步 · 让账单能生成并展示（4d，D5 + D3）

### 这一步在解决什么问题

把 `TripEnded` 事件变成一张**唯一**的账单，并提供给收银台展示。

**这里是全项目最关键的域边界**：账单由 billing 域的消费者生成，订单域只发事件。这一步如果写成"end 接口里顺手 INSERT bill"，看似省事，实际上是把计价能力塞进了订单服务 —— 以后改计价规则要动两个服务，且订单服务会依赖账单表结构。

---

### 内部能力 13-0：消费 `TripEnded` 生成唯一账单

- **作用**：把行程数据 + 价格快照换算成一张账单。
- **落库**：`bill`（`state` 初始 `CALCULATING` → 核算完成 `UNPAID`）
- **规则**：
  1. **同一 `order_id` 只生成 1 张行程账单**（唯一约束兜底）
  2. 金额全部来自**下单时冻结的价格快照**，不重新读当前配置
  3. 账单字段完整落：`T / Q / H / F / K / Cp / Cd / P / D / N`
  4. 事件重放不得产生第二张账单
- **注意** ⚠️
  - "送达时重新算一遍价"是错的 —— 规则改了会导致历史订单金额变化
  - 消费者必须按 `event_id` 去重
- **验证**：重复投递同一 `TripEnded`，`bill` 表仍只有 1 行

---

### 接口 13-1：获取收银台数据（文档 3.5.1）

- **接口地址**：`GET /api/v1/pax/pay/checkout`
- **作用**：把金额、可用券、支付渠道一次性返回给收银台页面。
- **入参**：`order_id`(必填)、`bill_type`(`trip` / `cancel`，必填)
- **出参**：`{ bill: { P, detail }, coupons, channels, zero_pay }`
- **落库**：`bill`、`coupon`、`order`（只读）
- **规则**：
  1. **金额来自账单，不来自客户端**，前端不可篡改
  2. 零元账单走内部 `ZERO` 渠道
- **注意** ⚠️：任何"客户端传 `payable` 字段"的设计都是漏洞，等于把收银台交给用户
- **验证**：篡改入参不影响返回金额；0 元账单 `zero_pay=true`

---

### 接口 13-2：发起支付（文档 3.5.2）

- **接口地址**：`POST /api/v1/pax/pay`
- **作用**：创建一笔支付尝试，把账单推入 PROCESSING。
- **入参**：`order_id`、`bill_type`、`channel`(`wechat`/`alipay`/`zero`)、`idempotency_key`
- **出参**：`{ bill_id, payable, pay_state }`
- **落库**：`bill`、`payment_attempt`、`event_log`
- **规则**：
  1. **同一账单同时只允许一个有效支付尝试**
  2. 状态机：`CREATED → PROCESSING → SUCCESS / FAILED / CLOSED`
  3. 超时 → 标 PROCESSING 并**主动查单**
  4. **15 分钟关单**；晚到成功进入**差异处理**，不双收不双记
- **注意** ⚠️：幂等键必须落在 `payment_attempt` 上并建唯一索引，不能只在 Redis 里判重
- **验证**：同账单并发两笔 → 第二笔被拒；`pay_state=PROCESSING`

## 第 14 步 · 收钱，且只能收一次（1.5d，D5）★红线

### 这一步在解决什么问题

支付是**唯一一个外部系统参与**的环节，也是最容易重复入账的地方。回调可能重复、可能乱序、可能被伪造。

**核心原则**：页面跳回不算成功，**只有验签通过的回调或可信查单结果**才能置 SUCCESS。

---

### 接口 14-1：支付回调（文档 3.5.3）

- **接口地址**：`POST /api/v1/callback/pay`
- **作用**：接收渠道的支付结果，把支付尝试推进到终态，并触发分账与记账。
- **入参**：`channel_trade_no`(必填)、`channel`(必填)、`sign`(必填)
- **出参**：`{ result: "SUCCESS" }`
- **落库**：`bill`、`payment_attempt`、`coupon`、`driver_fund`、`driver_income_entry`、`ledger_entry`、`event_log`
- **规则**：
  1. **验签必须过**；且**订单号 / 商户 / 币种 / 金额四项一致**才置 SUCCESS
  2. **回调幂等**：按 `channel_trade_no` **唯一约束去重**，重复成功回调不重复入账、不重复增加司机收益
  3. **唯一结清支付**：账单以首个成功结清事务的支付为唯一有效付款（`settlement_payment_id`）
  4. **额外真实扣款** → 登记「重复收款待退」**负债**并原路退回
  5. 支付成功即触发分账：`D = Q - K - Cd` 计入待结算 **U**
  6. 该接口**免鉴权但必须验签**
- **注意** ⚠️
  - 只验签不核对金额 = 攻击者可以用一分钱的真实回调把大额账单置成功
  - 去重必须靠数据库唯一约束，Redis 判重在重启后会失效
- **验证**：篡改金额的回调 → 拒绝；同一 `channel_trade_no` 回调 10 次 → `driver_income_entry` 只 1 条

---

### 接口 14-2：支付查单与关单（文档 3.5.4）

- **接口地址**：`POST /api/v1/pax/pay/query`（查单）、`POST /api/v1/pax/pay/close`（关单）
- **作用**：支付结果未知时的兜底 —— 主动问渠道，或者关掉这笔尝试。
- **入参**：`bill_id`(必填)
- **出参**：`{ pay_state }`
- **落库**：`payment_attempt`、`bill`
- **规则**：
  1. 超时先标 PROCESSING，**主动查单**
  2. 15 分钟关单
  3. 晚到成功进差异处理，不双收不双记
  4. **页面跳回不能作为支付成功依据**
- **注意** ⚠️：关闭的支付尝试不能再被回调置成功，必须走差异处理流程
- **验证**：关单后模拟晚到成功回调 → 账单不变，生成差异记录

## 第 15 步 · 回填恢复目标 + 把钱分给该拿的人（1.5d，D1 + D5）

### 这一步在解决什么问题

两个独立的收尾动作打包在这一步：

1. **`restore_target` 回填** —— 第 2 步登录时只有 `default` 分支可用，现在订单和账单都有了，可以把"活动行程 > 未付账单"两个分支真正实现。
2. **分账入账** —— 支付成功后，把 `D = Q − K − Cd` 计入司机的待结算桶 U，并写复式分录。

---

### 接口 15-1：获取登录后恢复目标（文档 3.1.3）

- **接口地址**：`GET /api/v1/auth/restore-target`
- **作用**：告诉客户端"这次登录该跳哪一页"—— 有行程回行程，有未付账单回收银台，都没有回首页。
- **入参**：header `Authorization: Bearer {access_token}`
- **出参**：`{ restore_target: { type: active_trip / unpaid_bill / default, order_id } }`
- **落库**：`order`、`bill`（只读）
- **规则**：
  1. 恢复目标**统一由服务端计算**，优先级固定：活动行程 > 未付账单 > 默认
  2. 前端只按返回结果跳转，**不自行判断**
  3. 覆盖三条路径：乘客首页 / 司机大厅 / 资料补齐页
- **注意** ⚠️：这一步是"回填"，所以第 2 步已经上线的登录接口要同步联调一次，确认前两个分支真的命中
- **验证**：三类账号分别命中 `active_trip` / `unpaid_bill` / `default`

---

### 内部能力 15-2：分账入账 + 复式记账

- **作用**：乘客付的钱按规则拆成司机应得、平台净额、补贴差额。
- **落库**：`driver_fund`（U 增加）、`ledger_entry`（借贷两行）、`driver_income_entry`（明细）
- **规则**：
  1. `D = Q − K − Cd` 计入**待结算 U**，不是可用 A
  2. **复式记账**：每张凭证借方合计 = 贷方合计，只追加，**错误用反向冲正，不改原流水**
  3. 逐单满足资金守恒：`P = D + N + G`
  4. 渠道费默认平台承担（`Gd = 0`）
  5. 事件去重键防重复累计
- **注意** ⚠️
  - U 和 A 是两回事：支付成功只入 U，日结后才转 A。提前入 A = 司机可以提现还没结算的钱
  - 分录只追加。任何 UPDATE 分录的写法都会毁掉对账能力
- **验证**：抽 20 单逐单验证 `P = D + N + G`；`ledger_entry` 借贷合计相等

## 第 16 步 · 让司机看得到钱（2.5d，D5）

### 这一步在解决什么问题

钱已经进 U 桶了，现在要让司机能查到，并且把 U 转成可提现的 A。

顺序：**收益中心（只读展示）→ 流水明细（只读）→ 日结（写操作，U→A）**。先做只读再做写，是因为写错了看不到，只读的口径先定死，日结才有对照基准。

---

### 接口 16-1：获取收益中心数据（文档 3.10.1）

- **接口地址**：`GET /api/v1/drv/income`
- **作用**：司机一屏看到今天/昨天接了多少单、挣了多少钱、钱现在在哪个桶里。
- **出参**：`{ today_done, today_income, yesterday_done, yesterday_income, fund: { U, A, Fz, W, Debt }, pending_estimate, entries }`
- **落库**：`driver_fund`、`driver_income_entry`、`order`、`bill`（只读）
- **规则**：
  1. **完单量按行程结束日**计数，**收入按记账日**记账 —— **两个口径不同步属正常**
  2. 拼车两乘客算 **2 单**
  3. 完单量只计**当日 ENDED 且实际发车**的个人订单
  4. 差额明确"多/少/持平"，**支持负值**
  5. **昨日 0 元不显示百分比**
  6. 收益事件驱动首页统计，**10 秒内更新**
- **注意** ⚠️：第 1 条是最容易被当成 bug 上报的正常现象，接口文档和日志里要写清口径
- **验证**：构造"行程结束在今天、支付在明天"的订单，完单量与收入分别落在两天

---

### 接口 16-2：收入流水查询（文档 3.10.2）

- **接口地址**：`GET /api/v1/drv/income/entries`
- **作用**：让司机逐笔核对自己的收入来源。
- **入参**：`filter`(选填，明细筛选)
- **出参**：`{ entries: [ { name, fen, t, type } ] }`
- **落库**：`driver_income_entry`（只读）
- **规则**：
  1. 支付成功记录司机行程收益：**原车费、乘客实付、平台/司机承担券、佣金、补贴、应得**
  2. **退款 / 处罚用反向记录，不改原金额**
  3. **凭证不可变**
  4. 事件去重键防重复累计
- **注意** ⚠️：退款不能用 UPDATE 原流水金额 —— 账目失去可追溯性
- **验证**：退款后原流水金额不变，新增一条反向记录

---

### 接口 16-3：结算批处理（日结）（文档 3.15.1）

- **接口地址**：`POST /api/v1/admin/settle`
- **作用**：把前一天已支付、无冻结的待结算 U 转成可用 A。
- **入参**：`business_date`(选填，默认前一日)
- **出参**：`{ settled_amount, diff_items }`
- **落库**：`settlement`、`driver_fund`、`ledger_entry`、`balance_snapshot`
- **规则**：
  1. 按**北京时间**每日结算，**次日 02:00** 处理前日已支付且无冻结的司机收益
  2. **先核渠道收付、再核分账明细**
  3. 差异 → 生成**差异单并挂起条目**
  4. **批处理幂等**：`(driver_id, business_date, version)` 唯一键，**重跑不重复转余额**
  5. 差异条目挂起**不影响其他条目继续结算**
- **注意** ⚠️
  - 幂等键必须含 `version`，否则重跑会插入第二条
  - 挂起 ≠ 失败，挂起的条目要能人工介入后继续
- **验证**：同日重跑两次，`driver_fund.A` 不重复增加；构造一条差异，其他条目仍结算成功

## 第 17 步 · 让司机能提现（1.5d，D5）

### 这一步在解决什么问题

把可用余额 A 变成预占 W，再走审批打款。

**必须排在第 16 步之后** —— 没日结就没有 A，没有 A 就没有可提现的钱。

---

### 接口 17-1：申请提现（文档 3.10.3）

- **接口地址**：`POST /api/v1/drv/withdraw`
- **作用**：司机发起提现申请，立即冻结对应额度。
- **入参**：`amount`(必填，分)、`idempotency_key`(必填)
- **出参**：`{ withdrawal_id, state, amount }`
- **落库**：`withdrawal`、`driver_fund`、`driver_income_entry`、`event_log`
- **规则**：
  1. **最低 1000 分**、**单笔最高 200000 分**、**日累计 500000 分且最多 3 次**受理
  2. 提交即**原子从可用 A 转提现预占 W**
  3. **≥50000 分需双人审批**
  4. 相同幂等键返回**原单**
  5. 失败或驳回 → 额度返还，但**当日受理次数不返还**
  6. 结果未知 → **保持预占并查单**
- **注意** ⚠️
  - "先查余额够不够再扣"是并发漏洞，必须用 `UPDATE ... SET A = A - ? WHERE A >= ?` 的原子条件更新
  - 第 5 条容易被漏：次数不返还是防刷单的硬要求
- **验证**：并发提现 4 次 → 第 4 次被拒；失败后额度回 A 但次数不回

---

### 接口 17-2：提现审核（文档 3.15.2）

- **接口地址**：`POST /api/v1/admin/withdraw/review`
- **作用**：财务初审 / 复核 / 打款 / 驳回。
- **入参**：`withdrawal_id`、`action`(`first`/`pay`/`reject`)、`reviewer_role`
- **出参**：`{ withdrawal_id, state }`
- **落库**：`withdrawal`、`driver_fund`、`ledger_entry`、`operation_log`
- **规则**：
  1. **风控先识别异常标签**；普通单人审核，大额（≥50000 分）**两人分离**
  2. 批准后以**唯一代付请求号**提交渠道
  3. **未知结果先查单，不释放**
  4. 明确失败 → 终结原单，按**统一释放路由**处理预占；用户重新申请生成**新提现单**
  5. 成功无回单 → 维持「成功待核销」**不再出款**
- **注意** ⚠️
  - "未知结果就释放预占"= 可能重复出款，这是资损级错误
  - 退回的用户要重新申请，不能复用原提现单号
- **验证**：构造未知结果，预占不释放；驳回后 W→A 且可重新申请新单

---

## 第 18 步 · 退款与资金流水（2d，D5）

### 这一步在解决什么问题

退款是最复杂的资金动作 —— 要按模式分摊给乘客、平台、司机，还要处理尾差。

**必须排在第 15 步之后**：退款分摊要读分账结果，统一释放路由要处理提现预占。

---

### 接口 18-1：退款审批与执行（文档 3.15.3）

- **接口地址**：`POST /api/v1/admin/refund`
- **作用**：把钱退给乘客，并按规则分摊这笔成本。
- **入参**：`order_id`、`amount`(分)、`mode`(`PROPORTIONAL` / `PLATFORM`)
- **出参**：`{ order_id, refunded, driver_bear, total_refunded }`
- **落库**：`order`、`order_refund`、`bill`、`driver_fund`、`ledger_entry`、`balance_snapshot`
- **规则**：
  1. **退款预占**：审批起预占金额，**累计成功 + 在途 ≤ 原实付**
  2. **同一订单同时只允许一笔退款**进入分摊与执行阶段
  3. **分摊引擎**：两种模式**锁定后不可改**
  4. **尾差**：`Round(D0 × (Rp + r), P0) − Round(D0 × Rp, P0)`（T14）
  5. **统一释放路由**：一个账户事务内，**先偿 Debt → 再补退款预占缺口 → 余下按来源回 U/A**
  6. 司机承担额不足 → 记 `Debt` 待追偿
- **注意** ⚠️
  - 释放路由的**顺序不能变**：先还债再补缺口，最后才回余额
  - 同一订单并发两笔退款 → 第二笔必须被拒，否则会退超过实付
- **验证**：尾差公式精确；并发两笔同单退款只有一笔成功；司机余额不足时生成 Debt

---

### 接口 18-2：资金流水查询（文档 3.15.4）

- **接口地址**：`GET /api/v1/admin/capital-flow`
- **作用**：财务按单号穿透查看一笔钱从乘客到司机到平台的完整流向。
- **入参**：`order_id` / `account_id`(选填)、`export`(选填)
- **出参**：`{ entries: [ { t, desc, debit, credit, balance } ] }`
- **落库**：`ledger_entry`、`balance_snapshot`（只读）
- **规则**：
  1. 所有实际资金变化记录**借贷平衡**凭证
  2. **只追加不修改**，错误用反向冲正
  3. 支持按单号穿透与导出
  4. 渠道费默认平台承担（`Gd = 0`）
- **注意** ⚠️：这个接口是**只读**的，任何"导出时顺便调整金额"的需求都应当拒绝
- **验证**：按 order_id 能穿透到所有相关分录

### 第 13–18 步 · 完成标志（资金闭环门禁）

- 20 单逐单 `乘客实付 = 佣金 + 司机收入 + 补贴` 成立。
- 连续两天日结后 U 归零、A 等于应结算额。
- `balance_snapshot` 与分录累加一致。

## 第 20 步 · 行程中的变更与取消（2d，D3）

### 这一步在解决什么问题

行程中会发生两类变更：改终点、取消。这两类都会**影响金额**，所以都需要乐观锁 + 重新计价。

**必须排在第 13 步之后**：取消要生成取消费账单，账单能力还没做时做这个只能写假单。

---

### 接口 20-1：申请修改终点（文档 3.4.4）

- **接口地址**：`POST /api/v1/pax/order/change-endpoint`
- **作用**：行程中换目的地，需要司机确认。
- **入参**：`order_id`(必填)、`new_end_id`(必填)、`version`(必填，乐观锁)
- **出参**：`{ new_end_name, new_price, old_price, expires_at }`
- **落库**：`order`（`changes` + version）、`poi`、`pricing_config`（只读）
- **规则**：
  1. 普通快车 / 专车行程中可变更终点
  2. **每单最多 2 次**
  3. **司机 30 秒内确认**
  4. **原子更新终点与路线版本**
  5. **拼车禁止单方改点**
  6. 固定价变更生成新总价**需双方确认**
- **注意** ⚠️：司机同意与行程结束并发时，只能有一个版本提交成功 —— 这正是乐观锁要拦的场景
- **验证**：第 3 次改点被拒；司机超时未确认失效；拼车单改点被拒

---

### 接口 20-2：行程分享（文档 3.4.5）

- **接口地址**：`POST`（创建/撤销）/ `GET`（访问）`/api/v1/pax/order/share`
- **作用**：把行程实时位置分享给家人，只读、脱敏、可撤销。
- **入参**：`order_id`(必填)、`action`(`create`/`revoke`，POST 时必填)、`token`(GET 时必填)
- **出参**：`{ share_token, expires_at }` 或 `{ route: 脱敏路线 }`
- **落库**：`share_token`、`order`
- **规则**：
  1. **令牌随机不可预测**，**不能由订单号推导**
  2. **最长 24 小时**，**订单结束 30 分钟后失效**
  3. **可即时撤销**；撤销/过期即时拒绝
  4. **访问限流每分钟 60 次**
  5. **脱敏车牌与起终点区域**
  6. 分享页**不含手机号、支付信息、聊天记录**
- **注意** ⚠️：用订单号做哈希当令牌 = 任何人拿到订单号就能看到行程
- **验证**：无法由 `order_id` 推导出 `token`；撤销后访问被拒；分享页响应内不含手机号

---

### 接口 20-3：获取取消报价（文档 3.4.6）

- **接口地址**：`POST /api/v1/pax/order/cancel-quote`
- **作用**：取消前先告诉乘客要收多少钱，30 秒内有效。
- **入参**：`order_id`(必填)
- **出参**：`{ fee, reason, expires_at, version }`
- **落库**：`order`、`pricing_config`（只读）
- **规则**：
  1. **待接单免费**
  2. **已接单先获取 30 秒有效报价再确认**
  3. **接单 120 秒内免费，之后 500 分**
  4. **行程开始后只能走安全提前结束**
  5. 报价**绑定订单版本、原因与费用**；确认时状态变化则**重新报价**
  6. **取消费与订单状态分开管理**（可已取消且账单待支付）
- **注意** ⚠️：第 6 条意味着"订单已取消"和"取消费未付"可以并存，取消逻辑不要顺手把账单也置成已付
- **验证**：接单 119 秒报价 0 分，121 秒报价 500 分；报价后订单状态变化 → 确认被拒需重新报价

---

### 接口 20-4：确认取消订单（文档 3.4.7）

- **接口地址**：`POST /api/v1/pax/order/cancel`
- **作用**：真正执行取消，并产生一系列副作用。
- **入参**：`order_id`(必填)、`version`(必填，报价时的版本号)
- **出参**：`{ order_id, state, cancel_bill }`
- **落库**：`order`、`coupon`、`dispatch_task`、`bill`、`order_timeline`
- **规则**：
  1. 确认时**校验版本（乐观锁）**，防止并发状态变更
  2. 副作用三件套：**释放券 → 调整派单任务（拼车组剔除该单）→ 生成取消账单**
  3. 行程中取消 → 走**安全提前结束**（记录原因与实际送达点，按已发生有效里程时长计费）
  4. 记录取消责任方：`passenger / driver / system / cs`
- **注意** ⚠️：副作用必须和状态变更同事务。券释放了但订单没取消 = 券凭空可用；订单取消了但券没释放 = 券永久占用
- **验证**：取消后券回到 AVAILABLE；拼车组同组其他订单价格不受影响；行程中取消按有效里程计费

---

## 第 21 步 · 让乘客能查订单和维权（2d，D3）

### 这一步在解决什么问题

订单走完之后，乘客要能回看、评价、投诉。

**必须排在第 13 步之后**：列表和详情都要读账单，账单口径没定之前做，出来的数字一定是错的。

---

### 接口 21-1：订单列表（文档 3.6.1）

- **接口地址**：`GET /api/v1/pax/orders`
- **作用**：乘客翻历史行程。
- **入参**：`filter`(全部/进行中/待支付/已完成/已取消)、`page` / `size`(每页 20)
- **出参**：`{ list: [ { id, type_name, start_name, end_name, state, amount, bill_state, created_at } ], total }`
- **落库**：`order`、`bill`、`poi`（只读）
- **规则**：
  1. **本人订单**按**下单时间倒序**每页 20 条
  2. **列表口径**：进行中是**行程状态维度**、待支付是**账单维度**
  3. 金额按阶段标明 **预估 / 应付 / 实付 / 退款后净实付**
  4. **禁止把未付显示成实付**
  5. 已取消但有取消费未付 → **可同时出现在"已取消"与"待支付"**
- **注意** ⚠️：DTO 必须显式带 `amount_kind` 字段，别让前端靠 `bill_state` 猜
- **验证**：UNPAID 账单的金额标为"应付"而非"实付"；已取消+取消费未付的订单在两个筛选里都能查到

---

### 接口 21-2：订单详情（文档 3.6.2）

- **接口地址**：`GET /api/v1/pax/orders/{order_id}`
- **作用**：一单的完整档案 —— 状态、账单、时间线、路线、司机快照、费用明细、支付退款记录。
- **落库**：`order`、`order_timeline`、`bill`、`order_refund`、`driver`、`poi`（只读）
- **规则**：
  1. **详情快照**：司机与车辆信息、计价版本取**下单时快照**
  2. 不随司机改资料或平台改价变化
  3. **不伪造状态回退**
  4. 历史信息保持快照，不随后台改动变化
- **注意** ⚠️：司机改了头像/车型后，历史订单详情仍显示当时快照 —— 这是对的
- **验证**：改司机资料后，历史订单详情不变

---

### 接口 21-3：提交评价（文档 3.6.3）

- **接口地址**：`POST /api/v1/pax/order/rate`
- **作用**：乘客给司机打分。

## 第 25 步 · 把管理端的真权限补上（2d，D6）

### 这一步在解决什么问题

前面所有 admin 接口（计价发布、司机审核、派单配置）都用**固定超管账号**跑通了 —— 这是刻意的，为了不在第 1 步就先花一周搭权限体系。

现在业务域都有数据了，才具备"验证权限真的生效"的条件。

---

### 接口 25-1：角色权限管理（文档 3.17.1）

- **接口地址**：`GET` / `POST /api/v1/admin/role`
- **作用**：定义七类角色各自能碰哪些菜单、按钮、接口。
- **入参**：`role_code`(必填)、`permissions`(数组)
- **出参**：`{ roles: [ { code, permissions } ] }`
- **落库**：`role`、`permission`、`operation_log`
- **规则**：
  1. 七类角色：超管 / 运营 / 审核员 / 客服 / 安全处理员 / 财务初审 / 财务复核
  2. **RBAC 三层鉴权**：接口层强制校验 + **对象级授权**
  3. **角色编码唯一且不可改**
  4. **删除角色前检查引用**
  5. **保留至少一个超管**
  6. 权限变更**下次请求立即生效**
  7. 权限同时控制菜单、按钮与服务端接口 —— **按钮隐藏不是鉴权**
- **注意** ⚠️：第 7 条是安全底线。只在前端隐藏按钮、后端不校验 = 直接构造请求就能越权
- **验证**：去掉按钮后直接 curl 调接口 → 403；删掉最后一个超管 → 拒绝

---

### 接口 25-2：用户管理（文档 3.12.1）

- **接口地址**：`GET`（查询）/ `POST`（限制）`/api/v1/admin/users`
- **作用**：运营查账号、限制违规乘客/司机。
- **入参**：`role`(选填)、`restrict_type`(禁新乘车/禁新接单/禁提现/登录风险限制)、`reason` / `scope`
- **出参**：`{ users: [ { id, phone_mask, role, restrict } ] }`
- **落库**：`account`、`driver`、`passenger`、`operation_log`
- **规则**：
  1. **手机号掩码展示**
  2. 限制类型**拆分**为四类，不是笼统一句"封禁"
  3. 每次操作**必须填原因与范围**
  4. **受限会话保留**：封禁不禁**进行中任务的安全入口与付款路径**，只禁新业务
  5. 限制与解除**留痕可追溯**
- **注意** ⚠️：第 4 条常被违反 —— 把司机封了却连行程中的紧急求助按钮一起封掉，是安全事故
- **验证**：被限司机仍能调用紧急求助与收款；限制与解除都有 operation_log

- **注意** ⚠️：任何"运营后台直接改订单状态/金额"的入口都是红线，必须走命令 + 留痕

## 第 27 步 · 报表（2d，D6）

### 接口 27-1：订单与流水报表（文档 3.16.1）

- **接口地址**：`GET /api/v1/admin/report/orders`
- **作用**：给运营看昨天的整体经营数据。
- **入参**：`date`(统计日期，T+1)
- **出参**：`{ metrics: { orders, completed, cancel_rate, gmv, net_paid, commission, subsidy, driver_income, net_income } }`
- **落库**：`order`、`bill`、`ledger_entry`（只读）
- **规则**：
  1. **T+1 每日 03:00** 汇总上一自然日
  2. **口径版本化**：报表必须显示**统计日期 + 截止时间 + 口径版本**
  3. **GMV 按行程结束日**、**净实付按支付退款记账日** —— **两个口径不混算**
  4. 当日未收敛订单标 **「未收敛」**
  5. **增量汇总**：从事件/流水表汇总，保证手工小样本可逐项对平（T29）
- **注意** ⚠️：报表和收益中心可能在同一天给出不同的收入数字 —— 这是口径不同，不是 bug，必须在返回体里带口径版本自证
- **验证**：手工构造 5 单，报表数字与明细逐项对平；未收敛订单有标记

### 接口 27-2：司机活跃与留存（文档 3.16.2）

- **接口地址**：`GET /api/v1/admin/report/driver-activity`
- **作用**：看现在有多少司机在线、历史活跃多少、留存如何。
- **出参**：`{ online_now, active_history, retention: { next_day, day7, day30 } }`
- **落库**：`driver`、`order`（只读）
- **规则**：
  1. **实时在线**取**近 60 秒**心跳
  2. **历史活跃**按当日**有效出车时长 ≥ 60 秒**
  3. 留存按**队列成熟分母**计算
  4. **队列未成熟显示「不适用」，不显示 0%**
  5. **空分母不显示百分比**
- **注意** ⚠️：第 4、5 条是数据诚信要求 —— 0% 和"不适用"是完全不同的信息

### 接口 28-1：注销账号（文档 3.1.7）

- **接口地址**：`POST /api/v1/auth/account-cancel`
- **作用**：主账号整体注销申请与撤回。
- **入参**：`action`(`apply`/`withdraw`)、`role`
- **出参**：`{ state: cooling_off / applied, cooling_off_until }`
- **落库**：`account`（+ **跨域只读检查** 6 个域）
- **规则**：
  1. 注销按**主账号整体执行**
  2. 需无**任何在途业务与债务**，检查项：
     - 在途行程
     - 未付账单
     - 在途退款
     - 未结工单
     - 司机未结算款
     - 余额 / 冻结 / 在途提现
  3. **任一存在即拒绝**
  4. **冷静期 7 天**，期内主动登录 → **撤回注销**
  5. 期满撤销令牌 + 脱敏资料，**保留账务关联**
- **注意** ⚠️
  - 第 2 条的检查**跨 6 个域**，必须走各域只读接口，**禁止直连别人的表**
  - "保留账务关联"意味着不能物理删除 —— 与软删除规则一致
- **验证**：逐个造场景验证 8 个检查项；冷静期内登录自动撤回
