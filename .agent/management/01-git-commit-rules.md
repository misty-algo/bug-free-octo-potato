# 规则 1：Git 提交与合并约束

> 适用范围：`bw-cli` 项目全部仓库操作。任何 AI 或人工提交都必须遵守本规则。
> 目标：让每一次提交可追溯、可回滚、可评审，合并前保证"项目跑得通 + 接口测试没问题"。

---

## 1. 分支管理规范

| 分支 | 用途 | 说明 |
|------|------|------|
| `main` / `master` | 稳定主分支 | 只接受合并，禁止直接 push 提交 |
| `develop` | 集成开发分支 | 各功能合并的汇聚点（如团队启用） |
| `feature/xxx` | 功能开发分支 | 命名如 `feature/order-status-machine` |
| `fix/xxx` | 缺陷修复分支 | 命名如 `fix/gateway-timeout` |
| `hotfix/xxx` | 紧急线上修复 | 从 `main` 拉出，修复后同时合回 `main` 与 `develop` |
| `refactor/xxx` | 重构分支 | 禁止与功能开发混在同一分支 |

- 分支名一律小写、用 `-` 分隔，禁止中文、空格、特殊字符。
- 提交前先确认当前分支，禁止直接在 `main` / `develop` 上开发。

---

## 2. 提交前检查（必须全部通过，缺一不可）

在 `git commit` 之前，AI / 开发人员必须完成以下检查，任何一项不通过都**不允许提交**：

1. **格式化**：`gofmt -l .` 与 `goimports -l .` 输出为空（无需要格式化的文件）。
2. **静态检查**：`go vet ./...` 无错误。
3. **编译通过**：`go build ./...` 全量编译成功（不得只编译单个包）。
4. **单元测试**：`go test ./...` 全部通过（被改动的包必须有针对性测试）。
5. **整个项目跑通**：按 `README.md` 的启动方式拉起 gateway 与各 service，确认服务正常启动、无 panic、日志无 ERROR 级启动失败。
6. **接口测试**：对本次改动涉及的接口执行接口测试（HTTP/REST 与 gRPC 均需覆盖），确认：
   - 正常入参返回预期结果；
   - 非法入参返回正确错误码；
   - 边界条件（空值、越界、超长、分页上下限）行为正确。

> 判断"项目是否跑得通"的硬标准：
> - `go build ./...` 通过；
> - `go test ./...` 通过；
> - gateway（默认 8080）及各 service（user-service 9001 等）可正常启动；
> - 本次改动的接口，用 `curl` 或接口测试工具实测通过。

## 3. 提交步骤（严格执行，逐步进行）

按以下顺序逐步执行，禁止跳步或合并多步：

### 3.1 查看变更
```bash
git status          # 查看工作区状态
git diff            # 查看未暂存改动
git diff --cached   # 查看已暂存改动
```

### 3.2 自审变更内容
- 逐文件确认：是否包含**不应提交**的内容（临时调试代码、`print`、硬编码密钥、本地配置文件、`.env`、二进制产物、`*.log`、`.DS_Store`、`tmpdiag/` 临时诊断文件等）。
- 确认没有把无关文件混入本次提交。

### 3.3 精确暂存（按需，禁止 `git add .` 无脑全加）
```bash
git add <具体文件或目录>   # 只暂存本次任务相关的文件
```

### 3.4 再次复核暂存区
```bash
git diff --cached      # 提交前最后一次审查暂存内容
```

### 3.5 提交
```bash
git commit -m "<规范提交信息>"
```

### 3.6 提交后验证
```bash
git log -1 --stat       # 确认提交范围正确
git status              # 确认工作区干净
```

## 4. Commit Message 规范（Conventional Commits）

格式：`<type>(<scope>): <subject>`

### 4.1 type 类型
| type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（不改行为） |
| `perf` | 性能优化 |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `build` | 构建/依赖变更（`go.mod`/`go.sum`/`Makefile`） |
| `ci` | CI 配置 |
| `chore` | 其它杂项 |
| `style` | 格式（不影响逻辑） |

### 4.2 scope 范围
- 使用模块/服务名，如 `order`、`user`、`gateway`、`driver`、`contracts`、`repo`、`service`、`handler`。

### 4.3 subject 要求
- 用祈使句，首字母小写，不加句号，50 字符内。
- 用中文或英文均可，但同一项目保持一致。

### 4.4 示例
```
feat(order): 新增订单状态机流转校验
fix(gateway): 修复请求超时未透传 context 的问题
refactor(repo): 抽取公共分页查询方法
build: 升级 gin 至 v1.10.0
```

## 5. 代码合并步骤（Merge Request / Pull Request 流程）

合并必须走 MR/PR，禁止直接 push 到受保护分支。步骤如下：

### 5.1 推送功能分支
```bash
git push origin <feature分支名>
```

### 5.2 创建 MR/PR
- 填写清晰标题与描述，说明：改动目的、影响范围、测试方式、关联工单/Issue。

### 5.3 合并前检查（MR 上必须全部绿灯）
1. **CI 通过**：构建、`go vet`、`go test`、lint 全部通过。
2. **冲突已解决**：与目标分支无冲突；解决冲突后必须重新走一遍第 2 节提交前检查。
3. **评审通过**：至少 1 名成员 approve（高危模块见下）。
4. **接口测试报告**：在 MR 描述中附上本次改动接口的测试结果。

### 5.4 高危变更强制双重评审
涉及以下内容时，必须**至少 2 名成员 approve**，且需专项说明：
- `pkg/contracts/` 事件契约、状态机常量、金额拆分（`TaskAmount`）。
- 支付、资金流转、退款、提现、结算。
- 鉴权、权限、数据库 DDL、`api/proto` 契约。
- `go.mod` / `go.sum` 依赖变更。

### 5.5 合并方式
- 优先 **Squash and merge**（压缩为单一提交，保持 `main` 历史干净）。
- 禁止在合并时夹带与 MR 主题无关的改动。

### 5.6 合并后
- 删除已合并的功能分支（远程与本地）。
- 确认 `main`/`develop` 仍可整体跑通（必要时重新执行第 2 节检查）。

---

## 6. 禁止行为

- ❌ 未通过第 2 节全部检查就提交或合并。
- ❌ 直接 push 到 `main` / `develop`。
- ❌ `git add .` 无脑暂存全部改动。
- ❌ 提交信息为空或写 "fix"、"update"、"tmp"、"111" 等无意义内容。
- ❌ 一次提交混杂多个不相关改动（多个功能/修复应拆成多次提交）。
- ❌ 提交包含密钥、密码、token、生产配置、二进制、日志、临时文件。
- ❌ 用 `git push --force` 覆盖共享分支（除非明确要求且已确认）。
- ❌ 在 `go build` / `go test` 未通过的情况下声称"完成"并提交。
- ❌ 合并前不解决冲突、不跑测试、不评审。
- ❌ 删除/改写历史（`rebase` 已推送的分支）影响他人。

---

## 7. 快速检查清单（提交/合并前逐项打勾）

- [ ] 当前在正确分支
- [ ] `gofmt` / `goimports` 通过
- [ ] `go vet ./...` 通过
- [ ] `go build ./...` 通过
- [ ] `go test ./...` 通过
- [ ] 整个项目可正常启动
- [ ] 本次改动接口已实测通过（正常 + 异常 + 边界）
- [ ] 暂存内容已复核，无多余文件
- [ ] 提交信息符合规范
- [ ] （合并时）MR 绿灯、冲突已解决、评审通过
