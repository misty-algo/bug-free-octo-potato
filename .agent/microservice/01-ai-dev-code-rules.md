# 规则 2：AI 开发代码约束

> 适用范围：AI 在 `bw-cli` 项目中的一切代码生成与修改行为。
> 目标：明确"什么可以交给 AI、什么必须人工"，防止 AI 私自改动核心高危逻辑，保证代码质量与项目风格一致。

---

## 1. 职责边界：AI 可以做什么、不可以做什么

### 1.1 AI 允许做（授权范围）
- 按已确认的契约、框架、命名规范，**实现**某个用例/接口/仓储的代码。
- 编写单元测试、接口测试。
- 修复已定位的、非高危模块的缺陷。
- 生成 `dto`、`model` 映射、`repo` 方法、`handler` 适配等**机械性、模板化**代码。
- 依据现有公共方法/工具包复用代码，而非重复造轮子。
- 补充注释、错误处理、边界校验。
- 在 `go build` / `go test` 通过后交付。

### 1.2 AI 禁止触碰（必须人工，或人工确认后 AI 才可辅助）
以下**核心高危逻辑**，AI 不得擅自生成、修改、删除，必须先经人工确认：

| 高危域 | 具体范围 |
|--------|----------|
| 资金/支付 | 金额计算、分账守恒（`TaskAmount`）、支付、退款、提现、结算、流水记账 |
| 状态机 | 订单六态（`WAITING/ACCEPTED/ARRIVED/IN_TRIP/ENDED/CANCELLED`）、司机四态（`offline/idle/busy/pre_occupied`）的流转规则 |
| 鉴权/权限 | JWT 签发校验、角色权限、越权控制 |
| 数据库 | DDL、表结构、字段新增/修改、索引、迁移脚本（详见规则 5） |
| 契约/协议 | `api/proto`、`api/gen`、`pkg/contracts/events.go` 事件契约与常量 |
| 依赖 | `go.mod` / `go.sum` 新增或升级依赖 |
| 框架/配置 | 分层结构、启动流程、`configs/config.yaml` 密钥与地址、`Makefile`、`Dockerfile` |

### 1.3 需人工评审的特殊情况
出现以下情形时，AI 必须**停下并请求人工评审**，不得自行决定：
- 需要新增全局变量、修改全局状态、跨模块直接调用其他模块的私有方法。
- 需要改动导出符号（函数名/结构体字段/接口签名），可能破坏他人兼容。
- 需要引入新的第三方库或新设计模式。
- 一次改动超过 3 个文件且逻辑不相关。
- 对既有测试的修改（尤其删改断言使测试"变绿"）。

---

## 2. 代码风格与命名约束

- AI 生成的代码风格必须与**项目现有代码完全一致**，禁止自创风格、自创命名、自创目录。
- 遵循现有约定：包名小写、导出符号大驼峰、私有小驼峰；`NewXxx` 构造、`mapXxxError` 错误映射、`toProto`/`toRecord`/`toDomain` 转换命名等。
- 注释遵循项目风格（中文业务注释 + 导出符号注释），禁止照搬英文模板或缺失注释。
- 金额一律用 `int64` 单位"分"（`Fen`），禁止使用 `float` 表示金额。
- 时间统一 `time.Time`，输出用 `time.RFC3339Nano` 或项目已有 `formatTime` 约定。

---

## 3. 代码质量约束

1. **复用优先**：优先复用项目已有公共方法、工具包、枚举、错误码（`pkg/errors`、`pkg/contracts`、各 `pkg/*x` 客户端），禁止重复实现相同能力。
2. **显式处理异常与边界**：空值、越界、参数非法、超时、下游失败、并发，必须显式处理，禁止静默吞错。
3. **禁止硬编码**：魔法数字、地址、密钥一律走配置（`configs/config.yaml` / Viper），禁止写死。
4. **禁止废弃/死代码**：不生成废弃 API、不安全函数、未使用导入、死代码、注释掉的废弃逻辑。
5. **函数与嵌套**：单个函数不宜过长，嵌套不宜过深，遵守项目代码规范；复杂逻辑拆分为私有方法。
6. **临时调试代码**：AI 生成的临时 `print` / 日志必须显式标注，提交前清理干净。
7. **禁止越权全局操作**：不得擅自新增全局变量、修改全局状态、跨模块直接调用内部私有方法。

---

## 4. 错误处理约束（结合项目 `pkg/errors`）

- 领域层错误在 `entity` 内以 `errors.New` 定义（如 `ErrOrderNotFound`）。
- `handler` 层统一用 `mapXxxError` 把领域错误映射为 `pkg/errors` 的 `AppError`（`InvalidArgument` / `NotFound` / `Conflict` / `Internal` 等）。
- 禁止在 `service` / `repo` 层直接返回 gRPC `status.Error` 或 HTTP 状态码。
- 禁止用 `panic` 处理可恢复错误；禁止忽略返回的 `error`。
- 下游/超时错误要包装并保留 `Cause`（`apperrors.Wrap`），便于排查。

---

## 5. 禁止行为（完整清单）

- ❌ 未经确认直接改动 `go.mod` / `go.sum`。
- ❌ 用"逐行翻译"方式把旧代码/其它语言代码搬成 Go。
- ❌ 静默删除或重命名他人代码的导出符号（破坏兼容性）。
- ❌ 一次性生成超大改动不拆步、不解释。
- ❌ 只写 happy path，不处理错误与边界。
- ❌ 在 `go build` 未通过的情况下声称"完成"。
- ❌ 改动核心高危逻辑（支付/状态机/鉴权/DDL/契约）不先人工确认。
- ❌ 自创目录、自创分层、自创命名、自创依赖，破坏项目既有框架。
- ❌ 修改测试用例让用例"通过"，而非修复被测代码。
- ❌ 删除或注释既有测试，以绕过失败。
- ❌ 引入与现有实现重复的工具函数/客户端。
- ❌ 写死密钥、IP、端口、金额常量。
- ❌ 使用 `float` 表示金额、用 `fmt.Sprintf` 拼 SQL。
- ❌ 修改 `pkg/contracts/events.go` 中已发布的事件常量/状态机取值。
- ❌ 提交未清理的调试日志、`print`、临时文件。
- ❌ 在 `handler` 层写业务逻辑、在 `service` 层写协议细节、在 `entity` 层写持久化。

---

## 6. AI 交付自查清单

AI 每次交付代码前必须自查并说明：

- [ ] 改动范围是否与任务一致，未夹带无关改动
- [ ] 是否触碰了高危域（若是，是否已人工确认）
- [ ] 是否复用了现有公共方法/错误码/客户端
- [ ] 异常与边界是否显式处理
- [ ] 是否硬编码了任何魔法数字/密钥/地址
- [ ] `gofmt` / `goimports` / `go vet` / `go build` / `go test` 是否全部通过
- [ ] 临时调试代码是否已清理
- [ ] 是否新增了不必要的全局变量/导出符号/依赖
