# business-agent.md — 核心业务不变量

> 前置：先加载 `core-agent.md`；涉及落库的改动同时遵守 `data-agent.md`。
> 适用场景：订单、计价、账单、支付、钱包、派单、营销任何核心链路代码。
> 这些是**事故级红线**：违反任何一条，出的不是 bug，是资损 / 重复扣款 / 超发事故。

---

## 1. 订单状态机（固定，MUST NOT 增删状态或自造流转）

```
PENDING → ACCEPTED → ARRIVED → IN_SERVICE → COMPLETED_UNPAID(已到达/结束计费) → UNPAID → COMPLETED
PENDING → NO_DRIVER（派单失败，可回到 PENDING 重呼）
任意非终态 → CANCELLED（记录责任方 passenger/driver/system/cs）
任意非终态 → SUSPENDED（风控挂起）
```

- 状态变更必须走**乐观锁**：`findOneAndUpdate({_id, status: 期望状态, version}, {$set:{...}, $inc:{version:1}})` 或 GORM 等价写法，失败即重试或报冲突，MUST NOT 读-改-写。
- 每次状态变更必须写一条 `order_status_logs`（from / to / 操作人 / 原因 / 时间），做到**任意一单可完整回放**。

## 2. 计价可追溯

下单时把命中的计价规则完整冻结进 `pricing_snapshots`，账单挂快照。**规则改价只影响新订单，历史订单金额永不变**。改价留痕（`version` + `effectiveTime`）。

## 3. 资金守恒（对账铁律）

每一单必须满足：**乘客实付 = 平台佣金 + 司机收入 + 平台补贴**（差额可解释为券成本）。任何涉及钱的代码，AI 必须说明自己的改动如何维持这个等式。

## 4. 支付与钱包

- 支付单必须带幂等键（`idempotentKey` 唯一索引），重复支付只扣一次，多余自动退回。
- 钱包余额变更用原子操作（`$inc` / `UPDATE ... SET balance = balance - ?`）+ 版本校验，**禁止先查后改**；提现后"提现金额 + 钱包余额"必须守恒。
- 订单支付 + 司机入账这类跨集合一致性用数据库事务；无事务条件时必须写补偿逻辑并显式标注。

## 5. 派单唯一性

高并发下**同一订单只能有一个司机接单成功**（Redis 分布式锁或数据库原子更新实现）。派单 15 秒超时自动转派、逐轮扩圈，全程落 `dispatches`（含候选、推送、应答明细）。

## 6. 营销防超发

限量券、邀请奖励的发放必须原子扣减库存（`$inc` 带 `where issuedCount < totalCount` 条件），MUST NOT 先查再插。

## 7. 三方服务 Mock 约定

地图 / 支付 / 短信 / 实名核身等三方服务未配置密钥时走 Mock Adapter，接口契约与真实实现一致，代码中必须有 `// ADAPTER: real|mock` 显式标注。**MUST NOT 在业务代码里写死假数据假装调通了三方**。

## 8. "本期不做"清单（MUST NOT 假实现）

顺风车、自动驾驶调度、境外业务、自营车队重资产——遇到相关需求，返回明确的"暂不支持"错误，`bizType` 预留扩展值即可。
